# Concept: 远程可达的 pi 个人助理（NAS 常驻 + 异地 Windows 客户端）

- **Slug**: pi-personal-bot
- **Created**: 2026-11-03
- **Recommended option**: Option A（SDK 内嵌 + 极薄服务 + 浏览器壳客户端）

## Options

### Option A — 最小的远程 pi：单容器内嵌 SDK + 极薄服务 + 浏览器壳

- **Sketch**: NAS 上起一个 Node 容器，进程内直接创建 pi 的 agent 会话（不经 TUI、不经 stdio 桥），对外只暴露「发一句话 / 收流式回复 / 看会话状态 / 中断」这几件事；工作目录挂载 NAS 的一个目录，pi 内置工具全部可用；客户端是浏览器打开同一个页面（Windows 上可用 Edge 应用模式变成一个窗口）。入口两条：tailnet 直连为主、Funnel 为应急，共用同一个服务端口。
- **Appetite**: small（数天量级），且刻意保留向上生长空间
- **Trade-offs**:
  - 赢：能力与 pi 内置集合完全一致（G2 直接成立，无需搬运任何插件）；链路最短、延迟最低（tailnet 直连，无中继跳数）；单容器，符合 G4。
  - 让：UI 只有最必要的对话与状态，没有会话树浏览器、没有文件上传、没有多设备配对流程；断线恢复要靠自己写（重连后拉状态）。
  - 风险：鉴权、限流、流式传输、容器内逃逸边界这四件事都得自己写对，没有现成框架兜底。
- **Rabbit holes**:
  - `bash` 全开 + 公网可达 = 远程命令执行面；容器边界、挂载卷范围、凭据可见性是范围爆炸的第一入口。
  - 流式输出与断线重连语义（尤其是切换入口后恢复对话）。
  - NAS 出网受限（github/npm 需代理），镜像构建方式会成为第一个卡点。
  - 挂载卷的 PUID/PGID 与 NAS 实际权限体系对不齐，会让「能写文件」这个验收项反复失败。

### Option B — 用 chord 应用框架搭（配对、会话、Web 界面一次拿到）

- **Sketch**: 用 pi 仓库自带的 chord `startServer` 起一个带 HTTP+WebSocket、设备配对、会话令牌、CSP、文件上传、web 前端托管的服务，每个会话一个 worker 进程，pi 作为其中一个上文运行；客户端仍是浏览器，但多了「配对一台设备」的流程。
- **Appetite**: medium（数周量级）
- **Trade-offs**:
  - 赢：鉴权、设备配对、会话令牌、CSP、文件上传、热重载全现成；多会话/多设备从第一天就有；安全基线比自建更厚。
  - 让：系统形状被 chord 的编程模型锁定（contract/plugin/principal/document 等概念），学习成本明显；chord 正在 v1→v2 迁移，存在跟随成本。
  - 风险：隧道/反代场景必须贡献 `relays`/`hosts` 白名单否则 403；隧道后所有远程客户端共用一个地址，`pairingsPerAddress=10` 会让远端配对被临时锁死。
- **Rabbit holes**:
  - 把「pi 内置能力」映射到 chord 的 worker/会话模型的适配层。
  - 框架版本的迁移与跟随。
  - 首次配对的可用性（隧道场景下的地址共享问题）。

### Option C — 不自建，直接用现成产品（不做这个 idea 的一种形态）

- **Sketch**: 不写服务端，装 OpenClaw（或等价产品）作为常驻个人助理，远程访问交给它内置的 Tailscale/SSH/配对能力；本项目只负责工作目录约定与安全配置。
- **Appetite**: small
- **Trade-offs**:
  - 赢：立刻可用，20+ 通道、桌面端、配对、沙箱、插件生态都是别人做好的；零维护代码。
  - 让：不是「基于 pi」；OpenClaw 的 agent runtime 已自研分叉，只留 pi 的 TUI 库，所以「能力等价于 pi 内置集合」这个目标不成立；自己的安全边界与工具集无法按需裁剪。
  - 风险：产品方向由上游决定，与「我要一个自己的、能按自己规则长的 agent」相冲突。
- **Rabbit holes**:
  - 无（本质是不写代码），但需求变更只能等上游。

## Recommendation

**选 Option A。** 理由直接挂到问题定义的目标与指标上：

- G2（能力等价）在 A 里是**结构性成立**的——进程内直接跑 pi 的 agent 会话，工具就是内置那 8 个，不需要移植任何东西；B 需要一层适配，C 根本不成立。
- G5（延迟可接受）在 A 里代价最小：tailnet 直连没有中继跳数，Funnel 的 1.3–2.9 秒是链路固有成本，不因方案变化而改善，所以越早把「快入口」做对越关键。
- G4（运维最小）A 是单容器 + 单卷；B 是「服务 + 若干 worker + 存储」。
- G3（安全可控）是 A 唯一的短板，但它是**可以显式补上的**（单令牌、容器隔离、挂载范围收敛、bash 的边界策略），而不是像 B 那样依赖框架默认值。
- 用户明确选了「不设上限、要能持续迭代」，因此 A 的定位不是「一次性的最小 demo」，而是**能力基座**：先让「远程 + 能力等价 + 可验收」这条主链闭环，再按需向 B 的方向长（多设备配对、多会话、上传等），而不是一开始就承担框架的复杂度。

Option C 作为对照组保留：如果 A 在验证阶段发现「鉴权与沙箱这层写不对」，切换到 C 是比硬扛更理性的止损。

## Out of Scope (for the recommended option)

- 插件 / 扩展 / skills / prompt templates / themes / MCP 的安装与分发。
- 多用户、账号体系、团队协作。
- IM 通道（Telegram / Discord / Slack）。
- 手机原生客户端。
- Windows 本机文件作为执行目标（本期 agent 只作用在 NAS 挂载卷；已确认为后续迭代候选）。
- TUI 交互复刻（主题、快捷键、状态栏）。
- 公网匿名访问。
- 7×24 生产级监控、告警、高可用与备份策略。
- 客户端安装器、自动更新、代码签名。

## Assumptions to Validate

> 2026-11-03 已在 NAS 上做了一次实现冒烟测试（`spike/`），下面的假设按实测结果标注状态。

- ✅ **已验证**：pi 的 TypeScript SDK 能在无 TUI 的容器进程内创建会话、启用内置工具、产出流式事件并通过 HTTP/SSE 输出。
- ✅ **已验证**：`node:24-bookworm-slim` 基线镜像可在 NAS 上构建（需 `--network host` + 本机代理 `127.0.0.1:7890`）。
- ✅ **已验证**：内置工具在 Linux 容器内行为完整（`bash` 执行、`write` 落盘到挂载卷）；`grep`/`find` 需显式传入 SDK `tools` 数组才启用，`powershell` 与 Linux 服务端无关。
- ✅ **已验证**：Funnel 可与现有 CouchDB 的 8443 共存（另起 10000 端口），且**支持 SSE**流式输出。
- ⚠️ **部分验证**：会话持久化成立（容器重启后同一 `sessionId` 续接），但「多会话 / 多设备」未测。
- ✅ **已验证**：真实模型链路成立——接入真实 OpenAI 兼容网关后，模型能自主选择并连续调用 `bash` / `read`，且多轮上下文可凭历史回答；凭据经环境变量注入、由 `models.json` 的 `${PI_API_KEY}` 引用，不写入文件。
- ❌ **未验证**：Windows 侧 tailnet 直连（本机未安装 Tailscale），因此「快入口 P50 < 2 秒」尚未被证实；已实测的公网入口路径为 1–3 秒量级。
